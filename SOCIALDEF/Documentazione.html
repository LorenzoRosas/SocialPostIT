01 Introduzione al Progetto

1.1 Cos'è Social PostIt

Social PostIt è una piattaforma social leggera sviluppata in Node.js, pensata come progetto didattico per esplorare le fondamenta dello sviluppo web full-stack. Permette agli utenti registrati di pubblicare post con testo e immagini, interagire con i contenuti altrui tramite like e commenti, e comunicare in tempo reale tramite chat.

L'intera applicazione gira su un unico file server (server.js) e salva tutti i dati su file JSON locali, senza necessità di un database esterno. Le pagine HTML vengono generate dinamicamente dal server usando il motore di template EJS.

ℹ️
Natura del progettoSi tratta di un progetto educativo. Non è progettato per uso in produzione su larga scala: la gestione della sicurezza è semplificata intenzionalmente.

1.2 Obiettivi e Scopo

  • Dimostrare il funzionamento di un server HTTP con Express in Node.js
  • Illustrare il rendering server-side con template EJS
  • Esplorare la persistenza dati tramite file JSON senza database
  • Implementare autenticazione base tramite cookie
  • Introdurre le comunicazioni real-time con WebSocket
  • Gestire upload di immagini tramite codifica base64

03 Registrazione e Login

3.1 Come Registrarsi

Per creare un account clicca su Registrati nella navbar. Inserisci un username unico e una password, poi clicca "Crea account". Il sistema verifica che lo username non sia già in uso, salva le credenziali in utenti.json e imposta automaticamente il cookie di sessione reindirizzando alla home.

⚠️
SicurezzaLe password vengono salvate in chiaro in utenti.json. Questo è accettabile per un progetto didattico ma non per un'applicazione reale.

3.2 Come Accedere

Clicca su Accedi nella navbar. Inserisci username e password. Se le credenziali sono corrette, il server imposta un cookie di sessione e reindirizza alla home. Se errate, appare il messaggio "Credenziali errate".

Il cookie di sessione contiene lo username codificato con encodeURIComponent e ha Path=/, quindi è valido su tutte le pagine del sito.

3.3 Logout

Clicca su Esci nella navbar. Il server invalida il cookie impostando la data di scadenza a gennaio 1970: il browser lo elimina immediatamente. Dopo il logout vieni reindirizzato alla home come utente non autenticato.

04 Creare un Post

4.1 Form Nuovo Post

Clicca su Nuovo Post nella navbar (visibile solo se sei loggato). Compila i campi disponibili:

  • Titolo — obbligatorio, max 120 caratteri, appare come intestazione della card
  • Contenuto — obbligatorio, max 2000 caratteri, con contatore in tempo reale
  • Immagine — opzionale, caricabile tramite click o drag&drop
  • Tag — opzionali, separati da virgola; il simbolo # viene aggiunto automaticamente

Dopo aver cliccato "Pubblica", il post viene salvato in posts.json con titolo, contenuto, autore, data/ora, tag, array likes e array commenti vuoti.

4.2 Aggiungere un'Immagine

Clicca sull'area tratteggiata o trascina un file immagine. Formati accettati: JPG, PNG, GIF, WEBP. Dopo la selezione:

  • L'immagine viene ridimensionata lato client a massimo 900px di lato
  • Viene compressa in JPEG con qualità 0.75 tramite un canvas HTML5
  • La stringa base64 risultante viene inserita in un campo nascosto del form
  • Un'anteprima viene mostrata nella pagina con pulsante di rimozione
📦
Come funziona base64L'immagine viene convertita in una lunga stringa di testo (data:image/jpeg;base64,...) che può essere salvata direttamente nel file JSON senza un sistema di storage separato.

4.3 Limiti e Validazione

  • Dimensione massima immagine originale: 5 MB — controllata lato client prima della compressione
  • Dimensione massima in uscita: 900px · qualità JPEG 75%
  • Limite body server: 10 MB (configurato in Express)
  • Titolo: max 120 caratteri. Contenuto: max 2000 caratteri (validazione HTML)

05 Home Feed e Interazioni

5.1 Visualizzazione Post

La home page (/) mostra tutti i post dal più recente al più vecchio. Ogni card include: titolo, badge autore (cliccabile per andare al profilo), data di pubblicazione, tag hashtag, testo, immagine (se presente), contatore like, contatore commenti e sezione commenti.

La barra di ricerca nella home filtra le card visibili in tempo reale per titolo, autore o tag. Premendo Enter si accede alla pagina di ricerca completa. Cliccando su un tag si applica il filtro automaticamente.

5.2 Like

Ogni post ha un pulsante ♥ con il contatore dei like. Il sistema funziona con AJAX: il browser invia una richiesta POST a /like in background, senza ricaricare la pagina. Il server risponde con il nuovo conteggio e lo stato del like.

  • Se non hai ancora messo like → il tuo username viene aggiunto all'array likes del post
  • Se hai già messo like → il tuo username viene rimosso (toggle)
  • Il pulsante si colora di rosa quando hai già messo like
  • Se non sei loggato, il contatore è visibile ma il pulsante non è presente

5.3 Commenti

Sotto ogni post c'è una sezione commenti visibile solo agli utenti loggati. Scrivi un commento nel campo di testo e premi "Invia". Il form invia una richiesta POST a /comment/:index che aggiunge il commento e ricarica la pagina. I commenti mostrano autore, testo e data. L'autore di un commento può eliminarlo tramite il pulsante "Elimina" (via AJAX).

L'autore di un post può eliminare il proprio post tramite il pulsante "🗑 Elimina" (visibile solo all'autore, via AJAX).

06 Chat Live

6.1 Accedere alla Chat

Clicca su Chat nella navbar (visibile solo se sei loggato). Appena apri la pagina, il browser stabilisce una connessione WebSocket con il server e riceve un messaggio di benvenuto. Tutti gli altri utenti connessi ricevono una notifica del tuo ingresso.

6.2 Inviare Messaggi

Scrivi un messaggio nel campo in basso e premi "Invia" o Enter. La barra emoji permette di inserire rapidamente emoji nel messaggio. Un indicatore "sta scrivendo..." appare agli altri utenti mentre digiti.

  • I tuoi messaggi appaiono allineati a destra con sfondo azzurro
  • I messaggi degli altri appaiono a sinistra con sfondo scuro
  • I messaggi di sistema (ingresso/uscita utenti) appaiono centrati

La chat non conserva la cronologia: i messaggi sono visibili solo agli utenti connessi in quel momento.

6.3 Tipi di Messaggi

08 Domande Frequenti (FAQ)

Posso vedere i post senza essere registrato?

Sì. La home page è pubblica. Puoi leggere tutti i post e i commenti senza fare login. Like, commenti, chat e creazione post richiedono l'autenticazione.

I messaggi della chat vengono salvati?

No. La chat usa WebSocket puro senza persistenza: i messaggi esistono solo in memoria durante la sessione. Se ricarichi la pagina o il server si riavvia, la cronologia è persa.

Posso usare la stessa username su più dispositivi?

Sì, ma l'autenticazione è tramite cookie nel browser. Ogni browser/dispositivo ha il proprio cookie e può fare login indipendentemente con le stesse credenziali.

Cosa succede se carico un'immagine molto grande?

Il controllo lato client blocca immagini sopra 5 MB. Anche le immagini accettate vengono compresse e ridimensionate a massimo 900px prima dell'invio, riducendo notevolmente il peso finale nel JSON.

Posso eliminare un post o un commento?

Sì. L'autore di un post può eliminarlo tramite il pulsante "🗑 Elimina" visibile nella card. L'autore di un commento può eliminarlo tramite il pulsante "Elimina" nella sezione commenti.

Il server funziona su Windows/Mac/Linux?

Sì. L'applicazione usa path.join(__dirname, ...) per costruire i percorsi dei file in modo compatibile con tutti i sistemi operativi.

Come funziona la ricerca?

La barra di ricerca nella home filtra localmente le card visibili per titolo, autore e tag. Premendo Enter o usando la pagina /search, si esegue una ricerca completa sul server che include anche estratti del contenuto dei post e risultati per profili utente.

09 Limitazioni Note

  • Password in chiaro — non c'è hashing. In produzione si userebbe bcrypt o argon2.
  • Cookie non sicuri — il cookie non ha il flag httpOnly né Secure.
  • No HTTPS — il server gira solo su HTTP locale.
  • Nessuna sessione server-side — non è possibile invalidare sessioni lato server.
  • File JSON come database — le operazioni sono sincrone e non gestiscono concorrenza. Su traffico elevato possono verificarsi race conditions.
  • Immagini in base64 nel JSON — con molti post con immagini, il file posts.json può diventare molto grande.
  • Chat senza storia — i messaggi non vengono persistiti.
  • Nessuna paginazione — tutti i post vengono caricati in una sola richiesta.

1.2 Software

Descrizione del Software

Social PostIt è un'applicazione web full-stack di tipo social network realizzata interamente in JavaScript, con Node.js come runtime server-side. Il sistema consente a utenti registrati di pubblicare post testuali corredati da immagini, interagire con i contenuti altrui tramite like e commenti, cercare utenti e post, visualizzare profili pubblici e comunicare in tempo reale tramite una chat basata su WebSocket.

L'applicazione non dipende da alcun database esterno: tutti i dati vengono persistiti su file JSON locali (utenti.json e posts.json). Le viste HTML sono generate dinamicamente dal server tramite il motore di template EJS. Il frontend non utilizza framework JavaScript: tutte le interazioni dinamiche (like, commenti, ricerca, chat) sono implementate con JavaScript vanilla e la Fetch API.

Scopo del Software

Il progetto nasce con scopo didattico: dimostrare come sia possibile costruire un'applicazione web completa e funzionale con strumenti minimali, senza framework frontend, senza ORM e senza un sistema di autenticazione complesso. Ogni componente del sistema è scelto per la sua semplicità e leggibilità, privilegiando la comprensibilità del codice rispetto all'ottimizzazione delle prestazioni.

ℹ️
Contesto d'usoL'applicazione è pensata per esecuzione locale su un singolo host. Non include le misure di sicurezza necessarie per un deployment in produzione (hashing password, HTTPS, rate limiting, validazione input rigorosa).

02 Architettura del Software

2.1 Descrizione dell'Architettura

Social PostIt adotta un'architettura monolitica a livelli (layered monolith) su singolo processo Node.js. Non ci sono microservizi, worker separati o code di messaggi: tutto il codice applicativo risiede in server.js e viene eseguito nel medesimo processo.

Il pattern seguito è MVC semplificato: il server Express gestisce le route (Controller), i file JSON fungono da Model, e i template EJS costituiscono il View. La comunicazione real-time è gestita dal protocollo WebSocket, agganciato allo stesso server HTTP tramite la libreria ws.

Browser
→
HTTP / WebSocket
→
Express + ws (server.js)
↓
EJS Templates (views/)
+
JSON Files (utenti.json, posts.json)

Il flusso di una richiesta HTTP tipica è: il browser invia una richiesta GET o POST → Express la instrada al route handler corretto → il handler legge o scrive i dati sui file JSON tramite i helper readJSONFile / writeJSONFile → per le route GET, EJS renderizza il template con i dati e invia l'HTML al browser; per le route POST-AJAX, il server risponde con JSON.

03 Analisi delle Priorità

3.1 Robustezza

La robustezza è garantita principalmente attraverso una difesa coerente contro input non validi e stati inconsistenti del filesystem.

  • Lettura dati difensiva — la funzione readJSONFile gestisce l'assenza del file, i file vuoti e il JSON malformato, restituendo sempre un valore di default sicuro invece di propagare eccezioni
  • Validazione indici — tutte le route che accettano un indice numerico (like, commento, elimina post) verificano che l'indice sia un intero valido e che esista nell'array prima di procedere
  • Protezione route private — le route che richiedono autenticazione controllano res.locals.currentUser e reindirizzano al login o rispondono con errore JSON se l'utente non è loggato
  • Sanitizzazione XSS nella chat — la funzione escapeHtml in chat.ejs converte i caratteri speciali HTML in entità sicure prima di inserire il testo nel DOM
  • Validazione autorizzazione — per eliminazione di post e commenti, il server verifica che l'utente corrente sia l'autore prima di procedere
⚠️
Limite: concorrenzaLe operazioni di lettura e scrittura sui file JSON sono sincrone e non atomiche. In caso di richieste simultanee, è teoricamente possibile una race condition che corrotta i dati. Questo è accettabile per uso didattico su singolo utente locale, ma non per ambienti multi-utente reali.

3.2 Usabilità

L'interfaccia è progettata per essere intuitiva e reattiva, con feedback immediato per ogni azione dell'utente.

  • Feedback visivo immediato — like e eliminazioni avvengono senza ricaricamento della pagina (AJAX); toast notifiche compaiono nell'angolo inferiore destro per confermare le azioni
  • Filtro locale dei post — la barra di ricerca nella home filtra le card in tempo reale senza chiamate al server, con contatore di risultati visibili
  • Tag cliccabili — ogni hashtag è un elemento interattivo che applica il filtro automaticamente al click
  • Autocomplete ricerca — il dropdown della ricerca nella home mostra suggerimenti di utenti e post con debounce di 300ms per limitare le chiamate API
  • Indicatore di digitazione — nella chat, gli altri utenti vedono chi sta scrivendo con auto-reset dopo 3 secondi di inattività
  • Barra emoji — nella chat, una barra di emoji comuni permette l'inserimento rapido senza dover aprire la tastiera emoji del sistema
  • Contatore caratteri — nel form di creazione post, un contatore mostra i caratteri usati sul totale disponibile, cambiando colore quando si avvicina al limite
  • Design responsive — tutte le pagine sono ottimizzate per dispositivi mobili tramite media query e layout flex/grid adattivi

3.3 Portabilità

Il progetto è progettato per funzionare su qualsiasi sistema operativo che supporti Node.js, senza dipendenze da servizi esterni o configurazioni specifiche della piattaforma.

  • Cross-platform paths — tutti i percorsi ai file JSON usano path.join(__dirname, ...), garantendo la correttezza sia su Windows (backslash) che su Unix (forward slash)
  • Porta configurabile — la porta del server si legge dalla variabile d'ambiente PORT con fallback a 3000, consentendo l'esecuzione in ambienti cloud senza modificare il codice
  • No dipendenze native — le uniche dipendenze npm (express, ws) sono scritte in JavaScript puro e non richiedono compilazione nativa
  • WebSocket auto-adattivo — il client rileva automaticamente il protocollo (ws:// o wss://) in base a window.location.protocol, funzionando sia su HTTP che HTTPS
  • Font via CDN — i font Google vengono caricati da CDN; in assenza di connessione, il browser ricade sui font di sistema senza rompere il layout

04 Design del Software

4.1 Principi di Design Adottati

  • Semplicità prima di tutto — ogni componente fa una cosa sola e la fa bene. Nessun livello di astrazione non necessario. Il codice è leggibile da chi ha una conoscenza base di Node.js.
  • Zero dipendenze frontend — nessun framework JavaScript lato client (no React, no Vue, no Angular). Tutte le interazioni dinamiche usano JavaScript vanilla e la Fetch API nativa del browser.
  • Server-side rendering — le pagine vengono generate completamente lato server tramite EJS prima di essere inviate al browser. Questo elimina la complessità di uno SPA e migliora il comportamento con JavaScript disabilitato.
  • Stato nei cookie — la sessione utente è interamente gestita da un singolo cookie HTTP (user=username). Non c'è stato di sessione sul server, rendendo il sistema stateless per le richieste HTTP.
  • DRY (Don't Repeat Yourself) — le funzioni helper readJSONFile, writeJSONFile e buildSearchResults sono estratte e riusate da più route. Il foglio di stile styles.css è condiviso da tutte le pagine tramite una route dedicata.
  • Feedback immediato — ogni azione dell'utente ottiene una risposta visiva entro pochi istanti, tramite AJAX, toast o aggiornamenti inline del DOM.

Il file server.js è l'unico file JavaScript lato server. Contiene, nell'ordine: import dei moduli, setup del server, configurazione Express, definizione dei percorsi JSON, middleware cookie, funzioni helper, e tutte le route HTTP seguite dal server WebSocket. Ogni sezione è delimitata da un blocco di commento titolato.

5.3 Commenti e Note Importanti nel Codice

Tutti i file sorgente sono commentati riga per riga in italiano. I commenti seguono una struttura gerarchica: blocchi di commento con titolo in maiuscoletto separano le sezioni logiche, mentre commenti inline su singola riga spiegano ogni istruzione significativa.

Le note tecniche più importanti inserite nei commenti riguardano:

  • Il motivo per cui si usa http.createServer(app) invece di app.listen() — necessario per condividere la porta con WebSocket
  • La spiegazione del meccanismo di autenticazione WebSocket tramite messaggio auth e il problema che risolve
  • Il pattern di calcolo dell'indice reale dei post (reversed.map((p, i) => ({...p, realIndex: i}))) usato in index.ejs
  • Il limite 10mb su Express necessario per accettare immagini base64
  • L'avviso che le password sono in chiaro (solo uso didattico)

5.4 Esempi di Utilizzo del Codice

Creare un nuovo post da form HTML

Il browser invia un POST a /post con i campi del form. Il server legge req.body, costruisce l'oggetto post e lo aggiunge all'array letto da posts.json:

javascriptserver.js — route POST /post
const posts   = readJSONFile(postsFile, []);
const newPost = {
    title:    req.body.title,
    content:  req.body.content,
    author:   res.locals.currentUser,
    date:     new Date().toLocaleString(),
    likes:    [],
    comments: [],
    tags:     req.body.tags
        ? req.body.tags.split(',').map(t => t.trim().replace(/^#/, '')).filter(Boolean)
        : []
};
posts.push(newPost);
writeJSONFile(postsFile, posts);

Toggle like via AJAX

Il client invia un POST a /like con il body postIndex=N. Il server risponde con JSON; il client aggiorna il DOM senza ricaricare la pagina:

javascriptindex.ejs — funzione toggleLike()
fetch('/like', {
    method:  'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    body:    `postIndex=${index}`
})
.then(r => r.json())
.then(data => {
    btn.querySelector('.like-count').textContent = data.likes;
    btn.classList.toggle('liked', data.liked);
    showToast(data.liked ? '♥ Post apprezzato!' : '♡ Like rimosso');
});

Connessione e autenticazione WebSocket

Appena il socket è aperto, il client invia il proprio username al server tramite un messaggio di tipo auth:

javascriptchat.ejs — socket.onopen
const currentUser = '<%= currentUser %>'; // iniettato da EJS

socket.onopen = function() {
    sendBtn.disabled = false;
    // Invia l'username al server — risolve ambiguità di sessione
    // in ambienti dove più browser condividono lo stesso host
    socket.send(JSON.stringify({ type: 'auth', username: currentUser }));
};

5.5 Snippet di Codice per le Proprietà Analizzate

Robustezza — lettura difensiva del JSON

javascriptserver.js — readJSONFile()
function readJSONFile(filePath, defaultData = []) {
    try {
        if (!fs.existsSync(filePath)) return defaultData; // file non esiste
        const data = fs.readFileSync(filePath, 'utf8');
        if (!data.trim())            return defaultData; // file vuoto
        return JSON.parse(data);                          // parse normale
    } catch (error) {
        console.error(`Errore lettura ${filePath}:`, error);
        return defaultData; // JSON malformato o errore I/O
    }
}

Usabilità — filtro post in tempo reale

javascriptindex.ejs — filterPosts()
function filterPosts() {
    const q = searchInput.value.trim().toLowerCase();
    let visible = 0;
    cards.forEach(card => {
        if (!q) { card.classList.remove('hidden'); visible++; return; }
        const query    = q.startsWith('#') ? q.slice(1) : q;
        const match    = card.dataset.title.includes(query)
                      || card.dataset.author.includes(query)
                      || card.dataset.tags.includes(query);
        card.classList.toggle('hidden', !match);
        if (match) visible++;
    });
    searchCount.textContent = q ? `${visible}/${cards.length}` : '';
}

06 Testing

6.1 Strategia di Testing

Il progetto non include un framework di testing automatizzato (come Jest o Mocha). La verifica del comportamento avviene tramite testing manuale funzionale, che si rivela adeguato per la natura e la dimensione del progetto.

La strategia copre i seguenti scenari:

  • Test di registrazione e login — verifica che username duplicati vengano rifiutati, che credenziali errate mostrino il messaggio di errore, e che il cookie venga impostato correttamente al login
  • Test CRUD post — verifica creazione con e senza immagine, con e senza tag; verifica che solo l'autore veda il pulsante elimina; verifica l'eliminazione e la scomparsa dalla home
  • Test like e commenti — verifica il toggle like (aggiunta e rimozione), l'aggiornamento del contatore senza reload, l'aggiunta e l'eliminazione di commenti
  • Test ricerca — verifica il filtro locale per titolo, autore e tag; verifica il dropdown di autocomplete; verifica la pagina di ricerca completa
  • Test chat WebSocket — verifica la ricezione messaggi in real-time, l'indicatore di digitazione, il contatore online, e l'identificazione corretta del mittente in sessioni multi-browser
  • Test profilo — verifica la visualizzazione delle statistiche e dei post, la distinzione tra profilo proprio e altrui
  • Test responsive — verifica il layout su viewport mobile (<480px), tablet e desktop

07 Deployment e Portabilità

7.1 Guida al Deployment

Il deployment per uso locale richiede solo Node.js e npm. Per un deployment su server remoto (es. VPS Linux) i passi sono:

1
Installa Node.js sul server
Versione 18+ raccomandata. Su Ubuntu: curl -fsSL https://deb.nodesource.com/setup_18.x | sudo -E bash - && sudo apt install nodejs
2
Copia i file del progetto
Carica server.js, styles.css, package.json e la cartella views/ sul server tramite SCP o Git.
3
Installa le dipendenze
npm install nella cartella del progetto.
4
Avvia il server
Per produzione, usa un process manager come PM2: npm install -g pm2 && pm2 start server.js. Questo garantisce il riavvio automatico in caso di crash.
5
Configura il proxy
Usa Nginx o Apache come reverse proxy per esporre la porta 80/443 e gestire HTTPS con un certificato Let's Encrypt.
⚠️
Prima di un deployment pubblicoImplementare obbligatoriamente: hashing delle password con bcrypt, HTTPS, cookie con flag HttpOnly e Secure, rate limiting sulle route di login, validazione input lato server, SameSite sui cookie.

7.2 Considerazioni sulla Portabilità

Il sistema è altamente portabile grazie alle scelte architetturali adottate:

  • Nessun database esterno — non occorre installare MySQL, PostgreSQL o MongoDB. I file JSON vengono creati automaticamente alla prima esecuzione.
  • Dipendenze minime — solo express e ws: due pacchetti stabili e privi di dipendenze native che richiedono compilazione.
  • Variabile PORT — la porta è configurabile tramite variabile d'ambiente, compatibile con piattaforme PaaS come Railway, Render, Fly.io.
  • Percorsi cross-platform — l'uso di path.join garantisce il funzionamento identico su Windows, macOS e Linux.

Il principale limite alla portabilità in ambienti cloud è la persistenza tramite file JSON: le piattaforme container (come Docker su Kubernetes) non garantiscono la persistenza del filesystem tra riavvii. In quel contesto sarebbe necessario sostituire la persistenza JSON con un database esterno.

08 Manutenzione del Software

8.1 Strategie di Manutenzione e Bug Fixing

Data la struttura monolitica e la ridotta dimensione del codebase, la manutenzione è relativamente semplice. Le strategie principali sono:

Localizzazione dei Bug

I log del server (console.error nelle funzioni helper e nei catch) forniscono il primo livello di diagnostica. Ogni errore di lettura/scrittura JSON viene loggato con il percorso del file e il messaggio di errore originale. Per i bug lato client, gli strumenti di sviluppo del browser (Console e Network) sono sufficienti per diagnosticare problemi AJAX e WebSocket.

Modifiche al Modello Dati

Aggiungere un campo a utenti.json o posts.json richiede di: aggiornare il punto in cui l'oggetto viene costruito (es. users.push({...}) in /signup), e aggiornare i template EJS che lo visualizzano. I dati preesistenti nei JSON non vengono migrati automaticamente: i campi mancanti vanno gestiti con l'operatore || (es. user.bio || "").

Aggiunta di Nuove Route

Ogni nuova route va aggiunta in server.js seguendo il pattern esistente: validazione dell'autenticazione, lettura dati con readJSONFile, logica applicativa, scrittura con writeJSONFile, risposta JSON o render EJS. Per route che richiedono un nuovo template, aggiungere il file .ejs nella cartella views/.

Aggiornamento Dipendenze

Le dipendenze (express, ws) sono mature e raramente introducono breaking changes nelle patch version. Per aggiornarle: npm update. Verificare che il comportamento delle route non sia cambiato dopo l'aggiornamento tramite test manuale delle funzionalità principali.

Backup dei Dati

Poiché i dati sono nei file utenti.json e posts.json, il backup consiste semplicemente nel copiare questi due file. Per un sistema in produzione, si consiglia un backup periodico automatizzato tramite cron job.

9.2 Suggerimenti Futuri per il Miglioramento

  • Sicurezza — hashing password con bcrypt, cookie HttpOnly e Secure, rate limiting sul login, validazione input lato server con una libreria come Joi
  • Persistenza — sostituire i file JSON con SQLite (tramite better-sqlite3) per gestire concorrenza e query più complesse senza dipendere da un server database esterno
  • Paginazione — caricare i post in blocchi (es. 10 per volta) con scroll infinito o paginazione classica, per scalare con molti contenuti
  • Storico chat — persistere i messaggi in un file JSON o database con rotazione automatica degli ultimi N messaggi
  • Sistema di notifiche — notifiche push per like e commenti ricevuti, anche quando si è su un'altra pagina
  • Testing automatizzato — introdurre Jest per test unitari sulle funzioni helper e Supertest per test di integrazione HTTP
  • Modifica post e profilo — permettere all'autore di modificare titolo, contenuto e tag di un post; permettere all'utente di modificare bio e avatar

9.3 Lezioni Apprese durante lo Sviluppo

  • La semplicità ha un costo nascosto — usare file JSON invece di un database è semplice da avviare, ma introduce limiti concreti (concorrenza, dimensione, query complesse) che emergono rapidamente con la crescita dei dati.
  • Il protocollo WebSocket richiede attenzione all'identità — il cookie HTTP letto durante l'handshake WS non è sempre affidabile in ambienti multi-browser sullo stesso host. La soluzione con il messaggio auth dimostra come un piccolo accorgimento possa risolvere un bug difficile da riprodurre.
  • Il CSS centralizzato paga — mantenere un unico file styles.css ha eliminato duplicazioni e reso coerente l'aspetto di tutte le pagine senza sforzo. Ogni modifica al tema si propaga automaticamente ovunque.
  • AJAX per le micro-interazioni migliora drasticamente l'esperienza — anche senza un framework frontend, usare fetch per like, commenti ed eliminazioni rende l'applicazione percepita come molto più reattiva rispetto a un approccio full-page-reload.
  • Il rendering server-side semplifica la gestione dello stato — non dover gestire lo stato dell'applicazione nel browser (come in React) riduce significativamente la complessità del codice client, anche se richiede reload della pagina per alcune operazioni.

10.1 Glossario

TermineDefinizione
ExpressFramework web per Node.js che semplifica la definizione di route HTTP e middleware.
EJSEmbedded JavaScript — motore di template che genera HTML dinamico inserendo dati JavaScript in file .ejs con tag <%= %>.
WebSocket (WS)Protocollo di comunicazione bidirezionale e persistente tra client e server su una singola connessione TCP. Usato per la chat real-time.
MiddlewareFunzione Express eseguita tra la ricezione della richiesta e l'invio della risposta. Nel progetto, il middleware cookie popola res.locals.currentUser.
res.localsOggetto Express disponibile in tutti i template EJS durante il ciclo vita di una richiesta. Usato per passare currentUser a tutti i template senza doverlo passare esplicitamente in ogni res.render().
AJAXAsynchronous JavaScript and XML — tecnica per inviare richieste HTTP dal browser in background tramite la Fetch API, senza ricaricare la pagina.
base64Codifica che converte dati binari (come immagini) in una stringa di testo ASCII. Permette di salvare immagini dentro file JSON.
JSONJavaScript Object Notation — formato di testo per lo scambio e la persistenza dei dati. Nel progetto usato come database.
CookiePiccolo dato testuale salvato dal browser e inviato automaticamente al server ad ogni richiesta. Usato per mantenere la sessione utente.
SSRServer-Side Rendering — generazione dell'HTML completo lato server prima di inviarlo al browser, al contrario di SPA dove l'HTML è generato nel browser.
DebounceTecnica che ritarda l'esecuzione di una funzione fino a che l'utente non smette di digitare per un certo intervallo. Usato nella ricerca per limitare le chiamate API.
XSSCross-Site Scripting — vulnerabilità che permette l'esecuzione di JavaScript malevolo iniettato nel DOM. Prevenuto nella chat con escapeHtml().
Race conditionSituazione in cui il risultato dipende dall'ordine temporale di operazioni concorrenti. Possibile con le scritture sincrone su file JSON in caso di richieste simultanee.
BroadcastInvio di un messaggio a tutti i client WebSocket connessi simultaneamente.
ToggleOperazione che alterna tra due stati opposti. Usato per like (aggiunge/rimuove) e per l'apertura/chiusura di elementi UI.
